# Architecture

## Meaning

`@wolfsblvt/icons` turns stable semantic names and source metadata into build-time SVG output. The architecture is organised around one invariant: selection and provenance are catalogue concerns, while framework rendering is an adapter concern. This document owns the current component boundaries, data flow, generated artifacts, and runtime assumptions across files.

## Components

| Component                   | Responsibility                                                               | Talks to                                                           |
| --------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| UI catalogue                | Maps shared aliases and validates direct Lucide references                   | Integration helper and `UiIcon`                                    |
| Brand catalogue             | Admits approved brand names and exposes source metadata                      | Integration helper and `BrandIcon`                                 |
| Product catalogue           | Reserves names, reports availability, and resolves accepted custom data      | Generated custom icon map and `ProductIcon`                        |
| Astro integration helper    | Produces the explicit `astro-icon` include set                               | UI and brand catalogues; consumer `astro.config.*`                 |
| Astro components            | Apply catalogue resolution, sizing, and accessibility defaults               | `astro-icon` for dependency icons; generated data for custom icons |
| Metadata files              | Record provenance, licence, trademark, colour-mode, and redistribution truth | Validation and catalogue modules                                   |
| SVG validator and generator | Enforce the authored source contract and generate compact runtime data       | `src/icons/` and `src/generated/`                                  |
| Contact-sheet generator     | Produces human optical-review surfaces                                       | Small upstream fixture copies and README assets                    |

## A UI icon request end to end

1. A consumer renders `<UiIcon name="settings" />`.
2. `resolveUiIcon` maps the semantic alias to `lucide:settings`.
3. The Astro adapter passes the validated name to `astro-icon`.
4. `astro-icon` loads the installed `@iconify-json/lucide` collection and emits SVG at build or server-render time.
5. No icon JavaScript, font, remote request, or catalogue payload is shipped to the browser.

An explicit name such as `lucide:heart` skips the alias map but still passes syntax validation. The consumer adds `heart` through `createAstroIconOptions({ extraLucide: ["heart"] })`, keeping server and hybrid bundles explicit.

## A brand request end to end

1. A consumer renders `<BrandIcon name="github" />`.
2. The brand resolver accepts only names present in the curated catalogue.
3. Metadata identifies the chosen Simple Icons slug, upstream revision, terms, and allowed presentation modes.
4. `astro-icon` resolves `simple-icons:github` from the installed local collection.

Consumers cannot use `BrandIcon` as an unrestricted Simple Icons gateway. Adding a brand changes shared product and legal truth and therefore requires metadata and review.

## A custom product icon request end to end

1. Original SVG source lives at `src/icons/products/<product>/<icon>.svg` and follows the 24-pixel Works contract.
2. Matching metadata under `src/metadata/products/` marks the icon available and records its standing.
3. `scripts/generate-custom-icons.mjs` validates the SVG and writes body data to `src/generated/custom-icons.ts`.
4. `ProductIcon` resolves `<product>/<icon>` and renders the body directly into an accessible SVG shell.

The initial custom canaries are still planned, so their resolver fails loudly rather than returning invented geometry.

## Data and storage

The package persists no user or application data. All inputs are repository files or installed package data. Generated outputs are deterministic from those sources:

- `src/generated/custom-icons.ts` from accepted custom SVGs;
- `fixtures/contact-sheet.html` from pinned fixture SVGs; and
- `docs/assets/readme/icon-pop.svg` from the same fixture sources.

The package lock owns exact transitive dependency resolution once generated by the repository bootstrap workflow.

## Boundaries and integrations

- **Astro:** peer and development host for the first rendering adapter.
- **Astro Icon:** peer rendering layer for Iconify collections.
- **Iconify JSON packages:** local data dependencies for Lucide and Simple Icons.
- **GitHub Actions:** advisory repository verification on pull requests and `main`.
- **No network runtime:** components never fetch icon data after the build starts.

## Invariants

- Public names are aliases or catalogue IDs, never repository file paths.
- Brands are unavailable until admitted with complete metadata.
- Planned custom icons never resolve as available assets.
- Works-authored source SVGs use `0 0 24 24`, `currentColor`, two-pixel round strokes, and no transforms, masks, filters, gradients, embedded text, scripts, or external references.
- Generated data is never the editable source of custom geometry.
- Decorative icons are hidden from assistive technology by default; informative standalone icons require an explicit label.
- Third-party geometry and marks do not inherit the MIT grant for original work.

## Known compromises

The initial visual fixture uses four small pinned upstream SVG copies so README and contact-sheet generation remains deterministic without downloading assets during generation. They are excluded from the package and recorded in third-party notices. Automated checks can reject structurally invalid custom SVGs, but optical quality, distinctiveness, brand fidelity, and comparison against neighbouring icons remain human visual judgments.
